# Pre-registration draft, 2026-11-07: task 48.27, row and column latents instead of cell attention

**DRAFT, 2026-11-07, before the arm trains.** Not yet in FINDINGS.md; to be merged there as its
own pre-registration before the kernel is pushed. Task: `openspec/changes/learn-from-peers/tasks.md`
48.27 (peer read 2026-11-06, FTFM, arXiv:2610.25558). Nothing here has been trained or scored on
a GPU; every GPU cost is ESTIMATED unless marked MEASURED. Style follows `preregs_2026-11.md`.

## What was built

- **Flag.** `ModelConfig.cell_mixing` (`"attention"` default, `"latent"`), `fintfm-train
  --cell-mixing`, `model.cell_mixing` in `default.yaml`. Default off: the parameter count and
  every forward path are unchanged (885,650 parameters at the reference recipe, as the control),
  and a checkpoint without the key loads with `"attention"`.
- **Design (paper spec only; no FTFM code or weights).** `LatentCellBlock` in
  `src/fintfm/modeling/model.py`, run `n_cell_blocks` times with tied weights, as the stock cell
  stages are. It replaces both the row-within-feature and the column-within-row stage. A learned
  query pools each row's unpadded cells into a row latent and each column's **context** cells
  into a column latent; row latents attend to one another under `_row_mask` (context rows only,
  plus self); column latents attend to one another with padded columns masked and no positional
  encoding; each cell then takes `cell + MLP(LayerNorm([cell, row latent, column latent]))`.
  Attention scores cost rows^2 and columns^2 per task, against features x rows^2 and
  rows x columns^2.
- **Refused combinations.** `latent` without `n_cell_blocks >= 1`; with `cell_row_attn="induced"`
  (a second row stage that would be dead weight); with `readout="cls"` (the readout tokens live
  inside the column attention this removes). Allowed: `attn_impl="split"` (it still selects the
  row encoder's attention only, and the reference recipe uses it), `pooling`, `n_summary_tokens`.
- **Parameters.** 923,618 at the reference recipe shape with `latent` (+37,968, +4.3% over the
  control's 885,650). The arm is not parameter-matched; the latent block is a new set of weights
  where the cell stage it replaces is a weight-tied pair. SMOKE-TEST count, CPU build.
- **Tests.** `tests/test_model.py` (default unchanged, no query reaches another row, column
  permutation, padded columns, chunked prediction, attention shapes, weight-decay exemption,
  checkpoint without the key, refused combinations) and `tests/test_train.py` (CLI trains two
  steps). Pipeline checks only; they say nothing about quality.

## SMOKE-TEST / CPU cost measurement (not the Verify's GPU measurement)

One forward plus backward step of `model.loss`, reference recipe widths (`d_cell` 48, `d_model`
128, 4 heads, `n_layers` 4, `n_cell_blocks` 1, `cell_labels`, `column_id_dim` 16), 2 threads,
fp32. The reference recipe's own shapes (batch 8, 136 features, up to 1,024 rows) need about
9 GB for cell attention's score matrices alone, so smaller shapes are stated. **The machine was
at a load average near 270 during the runs (other jobs), so the timings are noisy: the step times
below are the best of three steps in each of two repeats where two are given.** Peak memory is the
process's peak resident set (`ru_maxrss`), model and activations together.

| shape (batch, rows, features, context rows) | mode | seconds per step | peak memory, MiB |
| --- | --- | --- | --- |
| 2, 512, 64, 384 | attention | 1.15 and 1.45 | 1,151 and 1,173 |
| 2, 512, 64, 384 | latent | 0.43 and 0.18 | 766 and 788 |
| 2, 256, 32, 192 | attention | 0.30 and 0.34 | 574 and 521 |
| 2, 256, 32, 192 | latent | 0.07 and 0.44 | 480 and 448 |

Reading: at 512 rows by 64 features latent mode was faster in both repeats (2.7x to 8x, a wide
range because of the load) and used about 0.67 times the memory. At 256 rows by 32 features the
two repeats disagree (4x faster, then 1.3x slower), so no ratio is claimed there. Neither is
evidence about the 1.5x criterion on a T4: it is a different device, precision (fp16) and shape.

## The arm

- **Arm: `4827-latent-s0`.** `scripts/kaggle/ts_4827_latent_s0/`, a copy of
  `ts_au53_cell2_s0/` with only the lever flag (`--cell-mixing latent` in place of
  `--n-cell-blocks 2`), the arm name, and the kernel id and title changed. `COMMIT` is the literal
  `"PIN-AFTER-MERGE"`, so the kernel's `pip install` fails until it is set to the merge commit;
  it cannot be launched by accident. Not pushed; the Kaggle API was not called. It is not in
  `make_train_score.py`'s registry.
- **Recipe.** `configs/published/v4-cellattn-labels.yaml` (48,000 tasks, `n_cell_blocks` 1,
  `cell_labels`, rows drawn from {256, 512, 1,024}) with `--amp fp16 --attn-impl split --loader
  stream --ddp --batch-size 4` on a Kaggle T4x2 (global batch 8), `--seed 0 --steps 6000`,
  `--checkpoint-every 1000`, plus `--cell-mixing latent`. The recipe file pins every model key, so
  the kernel's `--cell-mixing` flag is the only difference from the control's configuration.
- **Control: `e1-v48-s0`** (`preregs_2026-11.md`, "Common to every arm"): same recipe, seed 0, 6,000
  steps, 48,000 tasks, same prior tasks, five-fold mean AP **0.1975** (0.2071, 0.2031, 0.1821,
  0.1734, 0.2215; §171 progress), scores in `runs/kaggle-ts-e1-v48-s0/e1-v48-s0/score/`, 0.525 s
  per step MEASURED (§171 progress). Reported beside it, as for the other arms: `e1-v48-s1`,
  0.1878.
- **Matched.** Steps 6,000, batch 8, so 48,000 tasks; seed 0; the same V4FinBench five full-panel
  folds and packaged inference defaults; the same scoring path in the kernel.
- **Primary measure.** Five-fold zero-shot V4FinBench mean AP first, then seconds per step and
  peak memory MEASURED on the same device (the kernel's `train.log` and `nvidia-smi`), compared
  with the control's 0.525 s per step. Per fold: `uv run python scripts/compare_v4_scores.py
  --cluster --control runs/kaggle-ts-e1-v48-s0/e1-v48-s0/score
  4827-latent-s0=runs/kaggle-ts-4827-latent-s0/4827-latent-s0/score`.

## Verify (from the task, verbatim)

> Verify: five-fold V4FinBench mean AP against the cell-attention control at matched steps, AP
> first, plus MEASURED seconds per step and peak memory on the same device; adopt only if AP is
> within the seed noise floor (0.0117, §173) on at least 4 of 5 folds and cost per step falls by
> at least 1.5x; falsified if AP falls below the control by more than 0.0117 on at least 3 of 5
> folds, or if the cost gain is under 1.5x at the context sizes we use (the latent route may only
> pay off where the table is large).

Reading of "within the seed noise floor": on a fold, arm AP is no lower than the control's by
more than 0.0117. Fixed here, before any result. A fold where the arm is higher counts as within.
One seed adopts nothing on its own under §175's rule; a seed-1 replicate follows an adopt result.

## Cost

- **GPU hours, ESTIMATED: 1.2 to 1.9 h for the one session** (train plus five-fold scoring).
  Basis: the control's whole sessions took 1.50 to 1.91 h, of which 0.6 to 1.1 h is installation
  and scoring (MEASURED, `preregs_2026-11.md`), and the control's training took 3,150 s (0.875 h).
  The upper end assumes the latent arm trains as slowly as the control; the lower end assumes a
  step about 1.5 times faster (the adoption bar) and scoring as before. The speed-up is not
  measured on a GPU; the CPU smoke test above is the only evidence, and it is noisy. A latent
  stage that is slower than the control would raise the upper end. Not scheduled in any lane.
- **Check during the run.** The step-1,000 line of `train.log` against the control's 525 s.

## What this does not decide

- Adoption on one seed; TabArena (V4FinBench first, CLAUDE.md); anything at 480,000 tasks.
- Whether the parameter difference (+4.3%) rather than the mixing explains a gap; a
  parameter-matched arm is not part of this task.
