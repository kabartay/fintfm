# V4FinBench inference arms on Kaggle GPU, pre-registration (draft, 2026-11-05)

**DRAFT, before any kernel is pushed.** Not yet in FINDINGS.md. Covers the open full-panel
V4FinBench runs of four tasks (`openspec/changes/audit-2026-10-15/tasks.md`): AU5.12, AU4.2,
AU4.3, AU5.8, each an inference-only change to the published checkpoint. Nothing here has run on
Kaggle; every cost is ESTIMATED unless marked MEASURED. A proxy or Lite result decides nothing
here (CLAUDE.md, "Score on the benchmark this project claims"); these runs are the credit number.

## What was checked first

- **Data on Kaggle is already established.** Every existing V4FinBench kernel
  (`task_dr311_ftleaf`, `task_au51_*`, `task_au41_boost_rounds`, `task_164_*`) mounts the
  dataset `sebastiantomczak10/v4-group-corporate-bankruptcy` (V4FinBench's own public Kaggle
  dataset, found at `/kaggle/input/**/company_years_h1.parquet`). FINDINGS lists V4FinBench as
  data under **CC BY 4.0** (Kostrzewa et al., arXiv:2605.10896; the protocol code is MIT) and
  §144-§147 already scored on it on Kaggle GPU. Nothing is staged by us: the kernels read a
  public dataset and download the public checkpoint `kabartay/fintfm-binary` (SHA-256 checked
  against `runs/v4-cellattn-labels.pt`). V4FinBench is Visegrad firms, so no SEC-filer overlap.
- **Pin: 62a73c3** (`git branch -r --contains` lists `origin/main`). Every argument the arms need
  exists in `src/fintfm/inference/classifier.py` at that commit: `ensemble_transforms` (with
  `squash`), `max_context`, `ensemble_class_shift`, `context_strategy="prototype"`,
  `prototype_minority_ratio`, `retrieval_per_class`, and `large_n` with `boost_pool_rows`
  (`inference/large_n.py`, `config.py`, `default.yaml`). `v4_protocol.py` is unchanged between
  62a73c3 and the current main (the intervening diff touches only `credit_*.py`).
- **References already exist for all five folds**, so no kernel reruns a reference arm. All are on
  the same full panel (200,361 test rows in fold 0 in each), and `compare_v4_scores.py` refuses a
  fold whose `y_true` or protocol settings differ.

  | reference | directory (local) | what it is |
  | --- | --- | --- |
  | `ens8` | `runs/v4-lever-ens8` | §196, 8 plain members, Mac CPU, d9bc7f0; has `company_test` |
  | default | `runs/lrsweep/eval-published` | the published one-member zero-shot arm (§194, §196, §200) |
  | `ft200` | `runs/ft/B_lr1e5` | §163's fine-tuned arm (AU5.8's named control) |

  Caveat, stated once: the references were scored on the Mac CPU (earlier commits, earlier days)
  and the arms will be scored on a T4 or similar. Same rows, same fold-seeded context
  sampling (`random_state=fold`); the comparison crosses platforms and days, as §194, §196 and
  §200 did, and a tiny numeric difference between devices is not controlled for. If a verdict sits
  within noise of a threshold, rerun the reference on the same GPU rather than argue it.

## Kernels

Generated by `scripts/kaggle/make_v4_inference_kernels.py` (arm YAML embedded;
`tests/test_v4_inference_kernels.py` fails if a kernel and its config drift). Each kernel:
horizon 0, `max_rows` none (full panel), `classical=("logistic_regression",)` as in the existing
kernels, no boosting baselines, no fine-tuning, `device="cuda"` and a refusal to run on CPU. One
overlay on every arm, `query_chunk: 512`, `feature_chunk: 8`: both are identity-preserving memory
knobs, and `task_dr311_ftleaf` found a 2,048 query chunk too large for a T4 after fine-tuning
(these arms do not fine-tune, so it may be unnecessary; it costs a little speed and cannot change
an output). Outputs land in `/kaggle/working/<arm>_<group>/`.

| arm (kernel dir `scripts/kaggle/task_v4inf_<arm>_<group>`) | change | config |
| --- | --- | --- |
| `tfsq8` (`f01`, `f23`, `f4`) | 8 members, `ensemble_transforms` (rank, squash) | `configs/arms/au512-ens8-tfsq.yaml` |
| `ctx900e3` (`f01234`) | `max_context` 900, 3 members | `configs/arms/proxy/au43-ctx900-ens3.yaml` |
| `au42proto` (`f01234`) | k-means prototype undersampling, ratio 0.3 | `configs/arms/au42-prototype.yaml` |
| `pc16` (`f01234`) | per-class retrieval, 16 positives | `configs/arms/au58-retrieval-pc16.yaml` |
| `boost` (`f0`, `f12`, `f34`) | 8 rounds of 512 rows, residual pool capped at 100,000 | `configs/arms/au58-boost.yaml` (new) |

Folds are grouped so that no kernel exceeds about 8 h ESTIMATED (one session is 12 h): the 8-member
arm and boost are split; the rest are one kernel each.

## Cost basis (ESTIMATED from one MEASURED timing)

MEASURED: `kaggle-fintfm-task-dr310-ft-noop` (T4, 5 folds in 13,645 s), after its fold 4
fine-tuning finished (12,348 s) the validation and test scoring of 1 member plus logistic
regression took 1,297 s, **about 0.36 h per fold** (the log's own timestamps, not a controlled
timing: the 2,048-row context, 1 member, about 400,000 scored rows per fold). Taken as the
one-member cost per fold, an upper bound because the logistic regression and fitting are in it.
Everything below multiplies that, and none of it was measured on the arm itself. On a quota of
30 GPU-hours a week (`docs/results/drafts/preregs_2026-11.md`), the five arms below total roughly
30 to 45 GPU-hours, so they do not all fit one week; the order below is the order of value.

## Order, adoption rules, estimates, scoring

Rules: the task's Verify where it states a V4FinBench rule, else §159's (five-fold mean AP
difference beyond the bar with at least 4 of 5 folds the same sign), with §173's 0.0117 yardstick
as the bar, which §196 and §200 used for inference arms. **A candidate** needs a five-fold mean
AP difference above +0.0117 with at least 4 of 5 folds positive; **harmful** under the mirror;
otherwise **null**. Fold-level Holm p (company bootstrap) is reported beside it. AP first, ROC-AUC
second; always the five-fold mean, never a single fold.

| # | arm | reference | GPU-h each kernel (ESTIMATED) | total |
| --- | --- | --- | --- | --- |
| 1 | `tfsq8` (AU5.12) | `ens8`, then default | f01 5.8, f23 5.8, f4 2.9 (8 x 0.36 h per fold) | 14.4 h |
| 2 | `ctx900e3` (AU4.3) | default | 2.4 (3 members at 900 rows, 1.35 x one member, per the draft's ratio) | 2.4 h |
| 3 | `au42proto` (AU4.2) | default | 1.8 plus k-means over a ~600,000-row pool per fold, unmeasured, so 3 to 4 | 3 to 4 h |
| 4 | `pc16` (AU5.8) | `ft200`, then default | 1.8 to 5.5 (0.36 h GPU-only; 1.1 h per fold if kNN-bound, as locally) | 2 to 5.5 h |
| 5 | `boost` (AU5.8) | `ft200`, then default | `f0` about 4 as a timing probe; `f12`, `f34` about 7 each, unmeasured | about 18 h |

Why this order: AU5.12 is the one task with a Lite gain waiting for a credit number, and its three
kernels are independent, so they can run in any order or in parallel sessions. AU4.3 and AU4.2 are
cheap. `boost` is last because its cost is a guess (draft: 8 to 25 h per fold uncapped); push
`boost_f0` alone first, read its wall time from the log, and push `f12` and `f34` only if it is at
or below about 4 h (then they fit a session). If fold 0 takes more, split further or stop.

**Checks during a run** (CLAUDE.md: a launch is not fire and forget). Within 15 minutes the log
must show `CUDA available: True`, `GPU: Tesla T4` (or P100), and the first fold's row count
(`1,000,087` rows in all, fold-0 test 200,361). Fold 0 of `tfsq8` should finish about 2.9 h in.

### 1. AU5.12, `tfsq8`

Question: do 8 members with transforms cycled over (rank, squash) beat 8 plain members on credit?
Lite said 20 / 6 / 1 (p 0.009, +0.01023 ROC-AUC). The proxy (`rank, power, squash`) said 12 / 4,
p 0.077. Verify (task): the label-symmetry probe recorded (done) and each axis scored on
TabArena-Lite (done); it states no V4FinBench rule, the task note says a five-fold run is needed
"before any default changes". Rule registered here: the common rule above, **against `ens8`**
(isolates the transforms) and, secondarily, against the default one-member arm, because §196 did
not adopt `ens8` itself (+0.0058). **Prediction (written before the run):** a null against `ens8`
(mean within +/-0.0117), because the Lite gain came from small general-tabular tables and the
credit panel's features are ratio columns that the rank transform already treats well.

Scoring (after pulling the outputs to `runs/kaggle-fintfm-task-v4inf-tfsq8-f01/` etc. and
gathering folds into one directory):

```bash
mkdir -p runs/v4inf/tfsq8
cp runs/kaggle-fintfm-task-v4inf-tfsq8-f01/tfsq8_f01/predictions_fold*.npz \
   runs/kaggle-fintfm-task-v4inf-tfsq8-f23/tfsq8_f23/predictions_fold*.npz \
   runs/kaggle-fintfm-task-v4inf-tfsq8-f4/tfsq8_f4/predictions_fold*.npz runs/v4inf/tfsq8/
cp runs/kaggle-fintfm-task-v4inf-tfsq8-f01/tfsq8_f01/v4_protocol.json runs/v4inf/tfsq8/
uv run --frozen python scripts/compare_v4_scores.py --cluster --control runs/v4-lever-ens8 \
  tfsq8=runs/v4inf/tfsq8 > runs/v4inf/cmp_tfsq8_vs_ens8.txt
uv run --frozen python scripts/compare_v4_scores.py --cluster --control runs/lrsweep/eval-published \
  tfsq8=runs/v4inf/tfsq8 > runs/v4inf/cmp_tfsq8_vs_default.txt
```

### 5. AU5.8 boost, `boost`

Same Verify and control as `pc16`. The residual pool is capped at 100,000 rows
(`boost_pool_rows`): a deviation from the uncapped method that the draft required to make the cost
finite, so the arm tests **capped** BoostPFN-style boosting, and a null here does not close the
uncapped method. Prediction: not a candidate. Gather folds from `boost_f0`, `boost_f12`,
`boost_f34` as in item 1, then:

```bash
uv run --frozen python scripts/compare_v4_scores.py --cluster --control runs/ft/B_lr1e5 \
  boost=runs/v4inf/boost > runs/v4inf/cmp_boost_vs_ft200.txt
uv run --frozen python scripts/compare_v4_scores.py --cluster --control runs/lrsweep/eval-published \
  boost=runs/v4inf/boost > runs/v4inf/cmp_boost_vs_default.txt
```

`compare_v4_scores.py` reads `company_test` from the arm's predictions (the references
`eval-published` and `B_lr1e5` lack it; `ens8` has it), so `--companies` is not needed.
