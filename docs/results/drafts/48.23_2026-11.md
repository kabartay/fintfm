# 48.23 audit: does the prior drop weak-signal or low-base-rate tasks? (draft, 2026-11-05)

Peer context: TabAbax (arXiv:2611.00562) filters generated tasks and names the loss of
weak-signal tasks as a limitation (`docs/paper/RELATED_WORK.md`, 2026-11-05).

## Verdict

**No filter acts at the published recipe.** One signal filter exists in code but is off
(`p_learnability_filter: 0.0` in `configs/published/v4-cellattn-labels.yaml`). The only always-on
guards are both-classes repairs and a base-rate floor that widen rather than narrow coverage.
So the task's Verify says: record and close, with a caveat for any future run that enables the
filter (below).

## MEASURED (seed 0, 2,000 binary tasks, recipe prior section, sizes 256/512/1024 uniform, `scripts/prior_filter_audit.py`, 417 s CPU, one process)

- Positive rate percentiles 1/5/25/50/75/95/99: 0.0010 / 0.0039 / 0.0117 / 0.0332 / 0.0959 /
  0.2383 / 0.2891. Shares: <0.5% 9.1%, 0.5-2% 29.9%, 2-10% 36.9%, >=10% 24.0%.
- Judge AUC (ExtraTrees 50 trees, 70/30 split, scorable tasks) percentiles 5/25/50/75/95:
  0.358 / 0.533 / 0.677 / 0.840 / 0.963. 11.2% of tasks are unscorable (a split side is
  single-class), 19.3% of all tasks score AUC <= 0.51.
- Both-classes repair (`financial.py:840`) fired on 17 of 2,000 draws (0.85%; counted by wrapping
  `Generator.choice`, so a coincidental identical call would inflate it slightly).
- Actual rejections/resamples at the recipe: 0 (filter off).
- What the **off** filter would do: it would reject 30.4% of draws overall (matches §125's
  "about a third"), and 52.4% of tasks with rate < 2% (n=781) against 16.3% of rate >= 2%. So the
  opt-in filter is exactly TabAbax's failure mode: it preferentially removes low-base-rate tasks
  (mostly through unscorable splits and chance-level AUC at a few positives).

## Implication

The published model was trained with weak-signal and low-base-rate tasks intact, so TabAbax's
stated limitation does not apply to FinTFM's published prior. Nothing to on/off test for the
current recipe: record and close. If someone later turns `p_learnability_filter` on, the §125
caution stands and the arm needs the following experiment (not run, ESTIMATED): train two
checkpoints at the recipe with `p_learnability_filter` 0.0 vs 1.0, matched seeds, same step
count, score both on V4FinBench five-fold mean AP; falsified if the change is inside 0.0117.
ESTIMATED cost: filter arm about 1.4x generation time per task (30% resampled, ExtraTrees fit
per draw; "under 30 minutes" over 48,000 draws per `mixture.py:230`) plus two T4 runs of 6,000
steps each, on the order of the §127 recipe cost per arm; no new data.
