# AU5.1: fine-tuning recipe at published scale (pre-registration draft)

**DRAFT, 2026-11-04, before any arm runs.** Not yet in FINDINGS.md; meant to be merged there as its
own pre-registration before the first kernel is pushed. Nothing here has been trained or scored.
Every cost is ESTIMATED from measured step times (MEASURED, quoted with their source).

## Why

§163's fine-tuning (200 steps, lr 1e-5, batch 2, 512 queries) gave +0.0076 mean AP over zero-shot,
5 of 5 folds positive (MEASURED, §163, five full-panel folds, 1,000,087 rows, 130 features).
§164 then found a second seed (+0.0071), 27 times more default labels per step (EN, +0.0009 over
§163's arm) and three times the steps (L600, +0.0024) all within the 0.0073 bar (MEASURED, §164).
All of §164 stayed at lr 1e-5, which is the bottom of the range Rubachev et al. 2025
(arXiv 2506.08982) sweep (5e-6 to 5e-4, early stopping on validation every 10 steps, patience 16).
AU5.1 asks whether the published scale, a higher rate with early stopping, moves V4FinBench AP.
Gap stated first: nothing here is expected to close the distance to untuned CatBoost (0.4005 mean
AP, §163; fine-tuned FinTFM 0.2062).

## Code (done, off by default)

Early stopping on inner-validation companies did not exist and is added to
`FinancialTFMClassifier._finetune` behind `inference.finetune_*` keys. Default `finetune_val_frac:
0.0` keeps the old loop; `tests/test_finetune.py::test_early_stopping_off_by_default_changes_nothing`
pins identical weights, and the config drift guard (`tests/test_config.py`) covers the new keys.

| key | default | meaning |
| --- | --- | --- |
| `finetune_val_frac` | 0.0 | share of the fit's training **companies** held out as inner validation; 0 = off |
| `finetune_eval_every` | 10 | steps between validation evaluations (Rubachev et al.) |
| `finetune_patience` | 16 | evaluations without a lower validation loss before stopping (Rubachev et al.) |
| `finetune_val_tasks` | 4 | fixed validation tasks, drawn once, reused at every evaluation |
| `finetune_val_query` | 1,024 | query rows per validation task |
| `finetune_val_pos_frac` | 0.1 | positives' share of validation queries, importance-weighted back to the true rate |

Selection uses only rows that `fit` receives: the held-out companies come from the fold's training
rows, never the fold's test rows and not the protocol's validation split (§163's Stage A used the
latter, which AU2.9 notes overlaps another fold's test rows). Held-out companies supply no
fine-tuning context or query. Step 0 (the zero-shot weights) is a candidate, so a run whose loss
never falls returns the unchanged model. The best weights are restored at the end. Validation loss
is the model's own cross-entropy (a proper scoring rule) on importance-weighted queries, not AP: a
pooled AP over 4 tasks would be noisier than the weighted loss at a 0.36% default rate (0.359%
positives in the panel, MEASURED, §164's logs). Per fold, `v4_protocol.json` records
`finetune_selection`: best step, stopped step and the full validation curve.
Tests (tiny model, CPU, 5 tests): curve recorded and best step is its minimum; best weights
restored (an absurd lr returns the step-0 weights and the caller's model is untouched); held-out
companies never appear in a fine-tuning draw; deterministic; arguments validated.

## Arms

One change from §163's setting per arm; everything else as §163 (batch 2, 512 queries, context from
`max_context`, no gradient clip, checkpoint `runs/v4-cellattn-labels.pt`, fold seeds as the
protocol). All three use the cap 3,000 steps, `val_frac 0.1`, `eval_every 10`, `patience 16`.

| arm | lr | config | kernels (folds 0-1, 2-3, 4) |
| --- | --- | --- | --- |
| `au51-lr1e5` | 1e-5 | `configs/arms/au51-lr1e5.yaml` | `scripts/kaggle/task_au51_lr1e5_{f01,f23,f4}` |
| `au51-lr3e5` | 3e-5 | `configs/arms/au51-lr3e5.yaml` | `scripts/kaggle/task_au51_lr3e5_{f01,f23,f4}` |
| `au51-lr1e4` | 1e-4 | `configs/arms/au51-lr1e4.yaml` | `scripts/kaggle/task_au51_lr1e4_{f01,f23,f4}` |

The kernels are generated by `scripts/kaggle/make_au51_kernels.py` (the arm's YAML is embedded, as
`task_164_l600` does; `tests/test_au51_arms.py` fails if a config and its kernels drift). They carry
the placeholder `UNPINNED` and refuse to run until regenerated with `--commit <sha>` of a **pushed**
commit that contains the early-stopping code (the kernels pip-install fintfm from GitHub at that
sha, like the §164 kernels). Fine-tuning is not pretraining, so `--checkpoint-every` does not apply.

**Confounds, stated now.** (1) 10% of the training companies are held out, so these arms fine-tune
on about 90% of each fold's training rows, which §163's arm did not; the stored inference context
is still drawn from all training rows. (2) The three arms are GPU runs against §163's CPU arm;
§164 measured the device gap at +0.0001 mean AP (largest per-fold +0.0004, MEASURED, §164), so
the device is not what decides a 0.0073 bar. (3) The `lr1e5` arm differs from §163's arm only in the
step cap, early stopping and the held-out companies; it is the control for "does early stopping
itself change anything".

## Decision rule (§159 and §164 Rule 3, unchanged)

Each arm is compared with §163's arm (`runs/ft/B_lr1e5`, fold 0 from `runs/ft/A_lr1e5`; the same
five folds and test rows; mean AP 0.2062). **Better** if the five-fold mean ΔAP exceeds the larger
of 0.0073 and twice the measured seed gap of the means (0.0010, S1, MEASURED, §164), so 0.0073,
with at least 4 of 5 folds positive (`scripts/c5_verdict.py helps` is this rule, two-sided).
**Worse** under the mirror condition; otherwise **no different**. The GPU device bar (twice the
0.0001 device gap = 0.0002) is below 0.0073 and does not raise it. Read average precision first;
ROC-AUC is reported beside it only.

What counts as a result:
- A verdict needs all five folds of an arm. Folds 0-1 alone are a partial, labelled as such, and
  settle nothing.
- Selection is on inner-validation loss only. The test-fold AP of any step other than the selected
  one is never computed, and no arm's rate is chosen after seeing test AP. Three arms are all
  reported; the family is three comparisons against one control with no family-wise correction
  (the same standing as §164's three), so a single arm barely over the bar is read as a lead, not
  a confirmed gain, until a second fine-tuning seed passes (one fold's seed gap reached 0.0013,
  S1, MEASURED).
- Report beside each verdict: per-fold ΔAP, the best and stopped step per fold, the validation
  curve's shape, and whether early stopping ever picked step 0 (an arm that returns zero-shot
  weights on a fold is a failed fine-tune there, not a null of the recipe).
- Also reported, not decisive: the arm against the GPU re-run of §163's setting
  (`runs/kaggle-fintfm-task-164-dev`, mean AP 0.2063) and against L600 (0.2086), both MEASURED, §164.
- Label every result "fine-tuned per dataset", never as the zero-shot FinTFM. This is verification
  on V4FinBench's held-out company folds, not a claim about any other dataset.

## Cost per arm (ESTIMATED)

Source figures (MEASURED, `runs/kaggle-fintfm-task-164-l600/fintfm-task-164-l600.log`, one Kaggle
GPU; the log does not name the GPU model): fine-tuning 600 steps in 3,424 s and 3,422 s on folds
0 and 1 (5.7 s/step, includes batch building); scoring one fold after fine-tuning about 1,400 s
(EN's log: about 1,260 s). Per fold fit time scales linearly with steps. Validation adds one
forward pass over 4 tasks every 10 steps; against a training step (a forward and backward over
2 tasks) that is roughly 8% more time (ESTIMATED, not measured).

| scenario (steps run per fold) | per fold | per arm (5 folds) | three arms |
| --- | --- | --- | --- |
| stops near step 600 | 1.4 GPU-h | 7.1 GPU-h | 21 GPU-h |
| stops near step 1,500 | 3.0 GPU-h | 14.8 GPU-h | 44 GPU-h |
| runs to the 3,000 cap | 5.5 GPU-h | 27.6 GPU-h | 83 GPU-h |

(Per fold = steps x 5.7 s x 1.08 plus 1,400 s scoring; where the stop falls is unknown and is what
the first kernels will show.) The cap is 5.5 GPU-h per fold, so two folds in one kernel is 11 h
against Kaggle's 12 h session limit: tight but inside it, which is why the fold groups are (0, 1),
(2, 3) and (4). A weekly quota of 30 GPU-h (preregs_2026-11.md) covers at most one arm at the
1,500-step scenario; the three arms do not fit one week unless early stopping fires well before
step 1,000. Staging that spends the least: launch the three `f01` kernels first (folds 0-1,
at most 33 GPU-h even at the cap, 8.4 at the 600-step scenario), read where each stops, then decide
which arms earn the remaining folds. Stopping after fold 1 is a labelled partial, not a result.

## Launch commands (owner, at the next GPU quota reset)

```bash
cd ~/proj/fintfm
# 1. push the commit that carries the early-stopping code (owner), then pin the kernels to it
git log -1 --format=%h                      # the pushed sha, say $SHA
uv run --frozen --extra bench --extra hf python scripts/kaggle/make_au51_kernels.py --commit $SHA
git add scripts/kaggle/task_au51_* && git commit -m "AU5.1: pin kernels to $SHA"   # as the owner

# 2. stage 1, folds 0-1 of every arm (three kernels; one at a time if quota is short)
for arm in lr3e5 lr1e5 lr1e4; do kaggle kernels push -p scripts/kaggle/task_au51_${arm}_f01; done
# (or scripts/kaggle/launch_queue.sh laneN task_au51_lr3e5_f01:v4-cellattn-labels.pt ...)

# 3. watch within 15 minutes: expect "fine-tuned N steps" and "inner validation: best step ..."
#    after the first fold's fit, and roughly 5.7 s/step (a rate well above that is a stalled run)

# 4. stage 2, the remaining folds of the arms that earned them
for arm in lr3e5; do for g in f23 f4; do kaggle kernels push -p scripts/kaggle/task_au51_${arm}_$g; done; done

# 5. score: per arm, copy the three kernels' predictions_fold*.npz into one directory
#    runs/kaggle-au51-<arm>/ (keep the f01 kernel's v4_protocol.json; keep the others as
#    v4_protocol_f23.json, v4_protocol_f4.json), then
uv run --frozen --extra bench --extra hf python scripts/c5_verdict.py helps au51-<arm> \
    runs/audit-cluster/ft163 runs/kaggle-au51-<arm>
```

If `c5_verdict.py`'s protocol check objects to the merged directory, report the per-fold ΔAP by
hand from the npz files under the same rule.

## Predictions (for scoring, not for steering)

None of the three arms is "better" by this rule: §164 found no lever beyond 0.0024 over §163's arm
at 200 to 600 steps, and the lr 3e-5 versus 1e-5 tie at 200 steps (validation AP 0.23247 both,
Stage A, MEASURED, §163) suggests a flat region. A higher rate (1e-4) is the arm most likely to
move in either direction. Open and not addressed here: a second fine-tuning seed, other query
sizes, and whether a different inner-validation share changes the stop point.
